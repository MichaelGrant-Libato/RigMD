# Finding and storage review

## Storage cleanup flow (0.2.8)

The storage modal now opens with **Free up storage space**, with direct preview buttons for temporary files, browser caches and downloaded update files. Installed-app removal remains available alongside these actions. Protected system/other storage stays informational, with a route back to cleanup; unavailable category totals never become invented recoverable space.

Personal categories now have an independent bounded scan of up to 20 large eligible content files, checkboxes with no default selection, a selected-file preview and explicit approval. Only backend-issued opaque file IDs are accepted. Known personal-folder roots are resolved on the PC; application/source/dependency files, system locations, alternate streams, path traversal, hard links, reparse points, cloud recall files and read-only files are excluded. Metadata previews bind volume/file identity, length, last-write timestamp, account, drive and selected warning. Replacement or modification needs a new preview. The scan reads metadata, not file contents.

Selected files are recycled by Windows `IFileOperation` from the same account's normal desktop helper, never by elevated `File.Delete`. Parent locations and exact file metadata are checked again at use time; the progress sink rejects non-recycle transfers, and success needs Windows recycle confirmation plus later file absence. There is no automatic permanent-delete fallback. Recycle actions do not claim recovered drive space. The preview warns that deletion in a synced folder can also propagate to cloud storage and other devices; this is not OneDrive's cloud-only **Free up space** action.

**Review Recycle Bin cleanup** is a separate preview and consent. It explicitly covers all current-account bin items on the selected drive, including items deleted outside RigMD. Windows' current count/size are shown and rechecked before execution. Changed bin readings invalidate the preview. Permanent emptying uses the normal-user helper and requires its own single-use approval; post-verification needs an empty bin and successful Windows result. Actual free space before and after is shown as an observation, not an attributed or guaranteed saving. Other accounts, drives and system files are not emptied.

The new endpoints live under `/api/autonomy/storage-cleanup`, keep local authentication and rate limits, and use the shared system-action gate. Preview/execute require current eligible, measured saved storage proof and current live pressure. Uncertain requests are not retried automatically. Operation receipts are persisted through the storage operation journal and recovered after a backend restart. Interrupted or uncertain operations remain unverified and are not replayed. Approvals are not restored or automatically reused.

App listing loads desktop registrations first, then enriches them with Store entries. A single bounded Store-provider worker cannot hold up the initial desktop list or accumulate workers when Windows stalls. A missing Store inventory leaves the desktop list usable and displays a partial-read message. Authorization/post-verification still requires the corresponding backend evidence.

New implementation files: `Services/StorageFilePolicy.cs`, `Services/StorageFileCleanupService.cs`, `Services/StorageCleanupWorker.cs`, `Services/WindowsRecycleOperation.cs`, `Controllers/StorageCleanupController.cs`, `frontend/src/components/StorageFileCleanup.tsx`, `frontend/src/lib/storageCleanup.ts`, `frontend/src/services/storageCleanupService.ts`. The existing storage review, app inventory, approval policy, helper startup, desktop lifetime and installer versions were updated. Tests are in `StorageFileCleanupTests.cs`, `StorageFindingActionTests.cs`, `LocalApiRateLimitingTests.cs` and `frontend/tests/storageCleanup.test.mjs`.

Manual checks: review temporary cleanup from the overview; scan Documents and select one disposable local file; confirm that preview alone changes nothing; approve recycling and verify that free space is not claimed as recovered; review the separate empty-bin preview without approving it unless all listed bin contents are disposable; confirm the before/after reading after a separately approved empty. Verify Alt-Tab clears approval while retaining the selected review. Native recycling/emptying is not executed by the automated fake-platform tests.

Windows references: [file operation flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags), [Recycle Bin readings](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shqueryrecyclebinw), [emptying a selected drive's bin](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shemptyrecyclebinw).

The remediation panel lists every saved warning under **Choose a finding to review**. Memory warnings share one app-closing review; storage volumes retain their own identities. Other warnings retain their recorded guidance. Missing, normal and informational readings do not authorize a change. Unsupported actions require a relevant check rather than a generic repair.

For a storage warning, **Review storage options** opens an internal review. Its action dropdown includes **Storage overview** and the existing cleanup actions. The wider app review uses one scrolling dialog with a paged app list and a preview/result panel; app names are not duplicated in a second selection label. Inventory limitations and original saved readings are collapsed by default.

The app inventory has radio buttons for choosing one app. **Check before removing** obtains fresh backend evidence. The user then explicitly approves the named app and presses **Remove this app**. Supported removal and its before/after evidence remain in RigMD; official uninstallers can show their own prompts. Windows Installed apps remains an explicit fallback when direct removal cannot be verified. Selection uses a backend-generated registration ID rather than list position. Refresh and filter changes clear selection, preview and approval. Filtering cannot leave a hidden app selected in the right panel; filters are disabled while previewing or running removal.

The current nontechnical labels are **Check before removing**, **Before removal**, **After removal** and **Remove this app**. Unsupported apps explain the limitation without displaying a disabled removal button. App versions, installation scope, raw installer codes and longer inventory caveats are available under details rather than repeated on every row. Availability never means “safe to remove.”

### Windows fallback for unsupported apps (0.2.6)

Selecting an unsupported or protected app shows **Open Windows Installed apps** in the right-hand panel. The button copies the selected inventory name during its user gesture and calls the existing authenticated, allowlisted `installed apps` navigation endpoint. It opens only `ms-settings:appsfeatures`; no registry command, executable path or app name is passed to a process launcher. The selected name is literal clipboard data and local UI context. The response summary is displayed only when the backend confirms success. Clipboard denial/unavailability does not prevent navigation and leaves instructions to type the exact name manually; clipboard waiting is bounded to two seconds.

Windows does not document a reliable per-desktop-app Installed apps link. The UI therefore explicitly asks the user to paste the copied name into Windows' search box, instead of claiming that Windows has automatically selected or filtered to the app. Microsoft's `appsfeatures-app` links concern supported app-features/package pages, and are not constructed from a desktop display name or unverified Store inventory ID. Any subsequent uninstall and permission prompt is handled in Windows. Navigation is read-only and does not create an uninstall success record, consume approval or mark a finding repaired. After changes, update the list and use **Check again**.

Reference: [Microsoft's Settings URI documentation](https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings).

Per-user uninstall records live in a shared registry branch and are read once using the default view. Previously, reading both 32-bit and 64-bit views assigned two different IDs to the same per-user record. Per-user IDs now use one canonical view; genuine machine-wide 32-bit and 64-bit registrations retain separate IDs. Apps are not merged merely because their display names match, so removal still targets one exact registration.

Alt-Tab still triggers an eligibility recheck. The same check's existing review remains mounted, retaining its chosen finding, filter, selection and scroll position. Changing actions and granting consent are disabled during verification; prior consent is cleared. A failed recheck keeps the review visible with actions blocked. A new proof revision, a different check, or a confirmed superseding result cannot inherit the old review's authorization.

## Storage overview and categories

The storage modal now starts with the selected drive's current capacity, used/free space and usage bar. Category rows open internal pages with a **Storage overview** back button. Installed apps retains the existing app preview/approval/outcome flow. Temporary files offers **Review temporary file cleanup**, which switches to the existing cleanup preview and separate approval. Documents, Pictures, Desktop, Music and Videos show read-only folder metadata and up to five largest files found. **Show more categories** expands the additional rows. Returning to the overview obtains a new reading; changing categories does not authorize a mutation.

`GET /api/autonomy/storage-overview?metricId=...` accepts only the existing storage metric IDs, resolves the corresponding fixed drive, and reads fixed current-account folder locations. It accepts no client-supplied path or command. Legacy `storage_usage` selects the Windows system drive. The endpoint uses the existing authenticated local API, scan/action rate allowance, a single concurrent scan gate, cancellation and `Cache-Control: no-store`. All folder enumeration shares a 15,000-entry/two-second traversal budget; operating-system I/O itself can exceed the elapsed-time budget. Paths outside the selected drive, missing and inaccessible folders remain unavailable. Links, junctions, offline files and cloud recall attributes are skipped; the reader opens no file contents and performs no deletion.

Folder readings are logical file lengths, not allocated disk space or promised recoverable bytes. Partial counts are visibly marked; an unknown size never becomes zero. Counts can overlap if Windows folders have been redirected to overlapping locations, so they are never summed into a drive total. App registration estimates remain separate and the installed-app page explicitly states that its inventory is not filtered by drive. System/reserved/other storage and cloud totals remain unavailable rather than being inferred from a remainder. This implements category navigation like Windows Settings; it does not reproduce Windows' private storage classification or Storage Sense controls.

Cloud/recall attribute reference: [Microsoft file attribute constants](https://learn.microsoft.com/en-us/windows/win32/fileio/file-attribute-constants).

### Storage overview checks

1. Open a current storage warning. Confirm the overview identifies that drive and reads current capacity/free space, then open **Installed apps**, **Temporary files** and **Documents** without leaving RigMD.
2. Use the back button and **Show more categories**. Confirm the drive summary refreshes, missing sizes remain unavailable, and incomplete counts are labeled. A selected D: finding must never display C: as its drive summary.
3. Open Temporary files and choose **Review temporary file cleanup**. Confirm the exact backend preview appears, consent starts unchecked, and no deletion occurs just from navigation.
4. Browse the app list and return. During a running uninstall the back button is disabled; closing/reopening the review still uses the existing operation recovery. Alt-Tab must retain the current category and existing app state while clearing consent during verification.
5. At narrow window widths, confirm cards, breadcrumbs, long file names and the app selection panel wrap without horizontal scrolling. Keyboard focus must move to the new page heading and category controls must remain reachable.

## App inventory limits

The authenticated local endpoint `GET /api/autonomy/storage-apps` reads desktop-app registration display metadata from the machine and current Windows account, using read-only registry handles. It inspects at most 2,048 desktop records, bounds display text, observes cancellation, reports partial reads, and returns no executable paths or uninstall commands. Windows packages come from `PackageManager.FindPackagesForUser`, bounded to 1,024 packages. Dependencies/resources are not presented as removable apps. A partial package catalog disables package removal. When native package inventory is unavailable, the legacy read-only `Win32_InstalledStoreProgram` provider can supply display-only entries without removal scope. The endpoint retains loopback/origin/credential checks and the autonomy rate limit. It does not invoke `Win32_Product` or run scripts. Inventory data is not sent to an AI provider.

The list sorts installer-reported size estimates, with unknown sizes last. These are not measured disk usage, selected-drive usage, or guaranteed recoverable space. Microsoft Store apps, portable apps, data files and other accounts may be missing. Under elevation with another account, “current account” means that Windows account.

Last-used dates, inactivity, desktop dependency relationships and removal safety are not established by these registrations. RigMD does not label apps unused or safe to delete, preselect candidates, delete app folders directly, or execute arbitrary uninstall commands stored in the registry. Names and publishers are metadata; availability is based on Windows installation metadata and backend safety checks. Recognized system/security names remain conservatively protected.

## Direct uninstall support and security

As of 0.2.7, removal supports eligible machine-wide Windows Installer (MSI) entries, verified Windows-registered desktop executable uninstallers, and eligible current-account Store packages. Recognized Windows, security, driver, runtime and shared-system entries remain protected. A Microsoft publisher alone is no longer a blanket prohibition on ordinary apps. There is no application-name allowlist and no preloaded app inventory. Per-user MSI installations remain unsupported. All methods can be refused by Windows, policy or fresh verification.

The backend resolves opaque app IDs from a fresh read-only catalog. It accepts no executable path, product code or command from the client. For MSI, registration, installer name, publisher, version, machine context and administrator role are checked again before execution. Ambiguous per-user registrations of the same product code are blocked. Windows Installer is launched from the absolute Windows system directory using a fixed argument list, a validated product GUID, quiet mode, restart suppression and disabled Restart Manager integration. No command interpreter, downloaded installer, script, DLL handler or unparsed registry command is launched. The desktop must already have Windows administrator permission; application consent remains separate.

Registered executable candidates require an absolute local fixed-drive executable, an identifiable uninstall operation, bounded separately parsed arguments, no command chaining/expansion, and no Windows/WindowsApps executable path. A selected preview verifies Windows Authenticode trust and exact normalized publisher/signer agreement, hashes the executable, and verifies the same account's medium-integrity desktop. Linked/cloud paths and `NoRemove` registrations are rejected. The executable and its directory ancestry are held against replacement during verification/launch. Approval binds the exact executable, arguments, file hash, signer and user SID; a changed target needs a new preview.

Official executable prompts run through a separate normal-user mode of the API apphost; that mode starts no HTTP server and refuses an elevated or different-account context. A private child environment carries the server-resolved target and is cleared before launching the vendor. The helper verifies the file again, then uses Windows ShellExecute on the exact executable and individual encoded arguments, allowing its manifest to request UAC normally. It never inherits the API's administrator token or silently falls back to it. The helper waits on the returned process handle. The API tracks the helper and its job descendants without killing them on handle close; the desktop's API lifetime job permits this explicit breakaway. Vendor handoffs through other Windows services are not a complete audit of every possible vendor side effect. A normal exit code alone never confirms uninstall.

Store removal uses `PackageManager.RemovePackageAsync` for the exact current-account package full identity. Framework/resource/optional/development/system-signed/unhealthy/unverified packages and packages required by another installed package are blocked. A complete package catalog and the same normal desktop account are rechecked before execution. No all-user removal, deprovisioning or forced policy bypass is requested. Windows can close the selected app and remove unused package dependencies; the preview discloses this. Windows enforces non-removable and organization restrictions. Store sizes remain unknown instead of fabricated.

Both preview and execution endpoints require a current eligible storage check and a measured selected storage warning. Fresh free-space readings must still show the selected warning. Approval expires after five minutes, is single-use, and binds the app identity/version, method/target, saved check and metric. The execution gate remains held while the uninstall is tracked, even if the HTTP caller disconnects or closes the review. A tracking failure keeps further system actions and ordinary desktop exit blocked. `POST /api/desktop/prepare-exit` atomically rejects exit while an action runs and prevents new actions once exit is approved; it uses the existing local API authentication. Polling reads in-memory operation status through a bounded authenticated read allowance; it does not spend scan/action permits.

Pre-execution and post-execution readings record the exact installation/package presence and available storage on fixed volumes. A successful installer exit alone cannot confirm removal: a later absent registration/package is also required, with incomplete inventory remaining unknown. MSI restart/cancellation codes are interpreted only for MSI; a vendor exit code of 3010 is not generalized to success. A canceled Windows elevation prompt is recorded as cancellation. Registration absence does not prove that all app data or shared files are gone, and free-space changes are observations rather than attributed app savings. The original diagnosis is not marked repaired automatically.

Storage uninstall and personal-file/Recycling Bin operation receipts are bounded and durably saved through `StorageOperationJournal` and `SqliteStorageOperationStore`. Approval tokens are not replayed after restart. An interrupted operation is marked unverified; current-boot uncertainty blocks further system actions and ordinary exit. After a verified Windows reboot, the saved outcome remains unverified and is not retried automatically. A missing or uncertain outcome never authorizes retry. The helper can outlive an API crash, so keep RigMD open until its outcome is known.

## Cleanup authorization

Storage actions from a mixed memory/storage check include a selected metric ID. The backend verifies that the selected saved reading exists exactly once in the latest available proof, has a warning status and valid percentage, and belongs to an explicit full, storage-component or storage-problem scope. Missing follow-up storage evidence cannot reuse an original warning. Hardware and review-only restrictions remain in force. The three cleanup tools retain their existing execution paths; app uninstall uses a separate operation and approval scope.

The backend creates a separate transient storage action context; it does not rewrite the saved primary diagnosis. Approval is bound to the session, selected metric, tool and arguments, expires, and can be consumed only once. Consent and current safety previews remain required. Tool completion and installer size estimates do not establish that a warning has cleared; take fresh readings afterward.

## 0.2.18 remediation correction

Windows Update download-cache cleanup now binds exact file identities and the initial stable service state to approval. It verifies stopping before deletion and restores/verifies that original state afterward, even after cancellation. Partial deletion and service-recovery failure remain unsuccessful. Generic legacy dispatch without this context is blocked. Temporary and browser-cache snapshot protections remain in place. These generic remediation attempts are distinct from the persistent uninstall/personal-file operation journal described above.

Explorer restart is now approval-bound to the actual current user's desktop shell, with replacement identity/window verification and no targeting of other sessions. Elevated desktop restart is blocked. Heat/battery/CPU workload findings give guidance and a separate-memory-check route rather than proposing unnamed app closure. Registry inventory is 19 tools (11 read-only, 8 approval-required changing tools) from one shared production/test registration list.
